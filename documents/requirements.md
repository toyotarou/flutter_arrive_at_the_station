# あの駅に着いたら (EKI NI TSUITARA) 要件定義書

> **要件定義書とは？**
>
> 要件定義書は設計書よりもさらに **上流** のドキュメントです。
> 「何を作るか」を決める前に「なぜ作るのか」「誰のために作るのか」「どんな課題を解決するのか」を定義します。
>
> **ドキュメントの位置づけ:**
>
> ```
> 要件定義書    →  基本設計書    →  詳細設計書    →  実装
> (なぜ作るか)    (何を作るか)    (どう作るか)    (コードを書く)
> ```
>
> | 観点 | 要件定義書 | 基本設計書 | 詳細設計書 |
> |---|---|---|---|
> | 主な読者 | 発注者・経営者・PM | PM・開発リーダー | 開発者 |
> | 記述レベル | ビジネス・業務の言葉 | 機能とシステムの言葉 | 技術・実装の言葉 |
> | 主な内容 | 目的・課題・要望 | 機能一覧・画面設計 | クラス・関数・DB定義 |
> | 例 | 「駅に着いたら知らせてほしい」 | 「F-01: 都道府県マップ表示機能」 | 「NativeGeofenceManagerで半径1000m・入場イベントを登録」 |

## 1. プロジェクト背景

### 1.1 背景

電車通勤・通学において、座席で居眠りしてしまい、降りるべき駅を乗り越すことがある。時刻指定の目覚ましでは対応しにくい理由として、以下がある。

- 電車の遅延・運休により、時刻が一定でない
- 乗り換えが多いルートでは、目的駅の到着時刻を正確に予測しにくい
- 毎回アラームをセットし直す手間がある

前作「降りタイマー (oriTimer)」では東京の路線に限定していた。しかし実際には地方出張・旅行・帰省など **東京以外** の路線を利用する場面も多く、全国どこでも使えるアプリへの拡張ニーズがあった。

また、駅を「地図から選ぶ」という直感的なUIを実現するため、日本地図の都道府県ポリゴン表示を活用した新しいアプローチを採用した。

同時に、開発者自身のスキル向上のため、以下の技術を実践的に学習する機会を求めていた。

- flutter_map による地図表示・ポリゴン操作
- Geolocator による現在地取得と近傍駅検索
- 全国駅データAPIの利用と、データ品質修正ロジックの設計

### 1.2 プロジェクト名

**あの駅に着いたら (EKI NI TSUITARA)**

## 5. 業務フロー（ユースケース）

### UC-01: 都道府県マップから駅を選択してアラームを開始する

```
目的:      電車乗車前に、降りる駅のジオフェンス監視を開始する
利用者:    エンドユーザー
事前条件:  アプリがインストールされ、初回起動済みである

基本フロー:
  1. ユーザーがアプリを起動する
  2. システムが日本地図（都道府県ポリゴン）を表示する
  3. ユーザーが目的地の都道府県をマップ上でタップする
  4. 選択した都道府県名と路線一覧ボタンが表示される
  5. ユーザーが路線一覧ボタン（電車アイコン）をタップする
  6. システムが選択都道府県の路線・駅一覧を表示する
  7. ユーザーが路線を展開し、降りたい駅を選択する
  8. ユーザーが「設定」ボタンをタップする
  9. システムがジオフェンスを登録し、監視を開始する
  10. ユーザーが電車に乗る（アプリをバックグラウンドにする）

代替フロー:
  7a. 駅名検索ボタンをタップし、駅名を入力して検索する
      → 検索結果の路線をタップして、路線リストへスクロールジャンプする
  7b. 路線図アイコンをタップし、路線全体の路線図（ポリライン）を地図に表示する
  7c. 路線全域アイコンをタップし、地図を路線全体が収まる範囲にズームする

例外フロー:
  6a. APIサーバーに接続できない場合
      → エラーメッセージを表示する
  8a. 駅が選択されていない場合
      → 「駅が選択されていません」エラーダイアログを表示する
```

### UC-02: 近傍駅から目的地を選択してアラームを開始する

```
目的:      現在地の近くにある駅をすばやく選んでジオフェンス監視を開始する
利用者:    エンドユーザー
事前条件:  位置情報パーミッションが付与されている

基本フロー:
  1. ユーザーがGPSアイコンボタンをタップする
  2. システムが現在地周辺の駅を地図上にマーカー表示する（デフォルト1km圏内）
  3. ユーザーが半径選択ボタン（1/3/5/10/20km）で表示範囲を変更する
  4. ユーザーが目的の駅マーカーをタップして選択する（赤くなる）
  5. ユーザーが「設定」ボタンをタップする
  6. システムがジオフェンスを登録し、ダイアログを閉じる

代替フロー:
  4a. 既に選択済みの駅をタップすると選択解除になる

事後条件: 選択した駅の半径1000m圏内に入ったとき、降車通知が発火する
```

### UC-03: 駅に近づいて降車通知を受け取る

```
目的:      選択した駅の近くに到達したことを通知で知る
利用者:    エンドユーザー
事前条件:  UC-01またはUC-02が完了し、ジオフェンス監視が起動中である

基本フロー:
  1. ユーザーが電車に乗り、選択した駅へ向かう（アプリはバックグラウンド）
  2. スマートフォンのOSが駅の半径1000m圏内への入場を検知する
  3. システムが音楽ストリームの音量を最大にする（Android のみ）
  4. システムがプッシュ通知を発火する（タイトル「降りる駅アラーム」、本文に駅名を表示）
  5. システムがループバイブレーションを開始する（最大強度・ユーザーが停止するまで継続）
  6. ユーザーが通知を確認し、電車を降りる準備をする
  7. ユーザーがAppBarの「stop」ボタンを押すと、ジオフェンスが解除され選択がリセットされる

代替フロー:
  2a. OSの省電力設定等によりジオフェンスイベントが遅延する場合
      → 遅延してでもイベント発火を試みる（即時性の保証はできない）
```

### UC-04: 監視を停止する

```
目的:      不要になったジオフェンス監視を解除する
利用者:    エンドユーザー
事前条件:  ジオフェンス監視が起動中である

基本フロー:
  1. ユーザーがAppBarの「stop（×）」ボタンをタップする
  2. システムが登録済みのジオフェンスを全件削除する
  3. システムがループ中のバイブレーションを停止する（Android のみ）
  4. システムがSharedPreferencesから選択駅情報を削除する
  5. 画面の「目的地：(未設定)」表示に戻る

事後条件: 以後、停止した駅に近づいても通知は発火しない
```

## 7. 非機能要件

### 7.1 性能

| 要件ID | 要件 | 基準値 | 備考 |
|---|---|---|---|
| NFR-01 | 都道府県マップの初期表示 | 3秒以内 | ローカルJSONからの読み込み |
| NFR-02 | 都道府県別駅データの取得 | 5秒以内 | ネットワーク環境・APIレスポンスに依存 |
| NFR-03 | 近傍駅の表示更新 | 10秒間隔 | GPSポーリング間隔（Timerによる定期実行） |
| NFR-04 | 駅圏内進入から通知発火まで | 可能な限り短時間 | OS・省電力設定に依存 |

### 7.2 可用性

| 要件ID | 要件 |
|---|---|
| NFR-05 | アプリがバックグラウンド状態・終了状態でもジオフェンス監視が継続すること |
| NFR-06 | APIサーバーが停止していてもアプリはクラッシュしないこと |
| NFR-07 | 通信エラー時はエラーメッセージを表示し、アプリが利用継続できること |

### 7.3 ユーザビリティ

| 要件ID | 要件 | 理由 |
|---|---|---|
| NFR-08 | 都道府県マップから駅選択まで直感的に操作できること | 路線名を知らなくても地図から選べるようにするため |
| NFR-09 | 到着通知のバイブレーションはユーザーが停止するまでループし続けること | 睡眠・居眠り中でも確実に覚醒できるようにするため |
| NFR-10 | 選択駅と現在距離が画面上で一目で分かること | 到着が近いことをリアルタイムで確認できるようにするため |
| NFR-11 | パーミッションが未取得の場合、適切なガイダンスを表示すること | ユーザーが操作に迷わないようにするため |

### 7.4 保守性

| 要件ID | 要件 | 理由 |
|---|---|---|
| NFR-12 | API接続先は1箇所で変更可能にすること | サーバー移行時の影響を最小化するため |
| NFR-13 | 画面とデータ取得ロジックは分離すること | 変更時の影響範囲を限定するため |
| NFR-14 | ファイルは役割ごとにディレクトリを分割すること | 目的のファイルを見つけやすくするため |
| NFR-15 | APIデータの品質問題はデータ修正ロジックで吸収し、UIコードと分離すること | APIの駅順・駅名の誤りを安全に補正するため |

## 8. 制約条件

### 8.1 技術的制約

| # | 制約 | 理由 |
|---|---|---|
| 1 | フロントエンドは Flutter で開発する | 学習目的。iOS・Android のクロスプラットフォーム対応 |
| 2 | 状態管理は Riverpod を使用する | Flutter公式推奨に準拠した学習 |
| 3 | 地図表示は flutter_map を使用する | オープンソース・OSM対応の地図ライブラリ |
| 4 | ジオフェンスは native_geofence パッケージを使用する | Flutterからネイティブジオフェンスを利用するため |
| 5 | 現在地取得は geolocator パッケージを使用する | 位置情報取得の標準的なFlutterパッケージ |
| 6 | 位置情報の「常に許可」パーミッションが必須 | バックグラウンドでのジオフェンス監視に必要 |

### 8.2 OSレベルの制約

| # | 制約 | 内容 |
|---|---|---|
| 1 | iOS: バックグラウンド処理制限 | iOSのバックグラウンドモードの制限を受ける |
| 2 | Android: 省電力モード | Dozeモードや省電力設定によりジオフェンスイベントが遅延することがある |
| 3 | 両OS: 通知パーミッション | ユーザーが通知を許可しなければ通知が届かない |
| 4 | 両OS: 位置情報パーミッション | 「常に許可」がなければバックグラウンドでのジオフェンス監視ができない |

### 8.3 リソース制約

| # | 制約 | 内容 |
|---|---|---|
| 1 | 開発者 | 1名（個人開発） |
| 2 | 予算 | 無料の範囲（サーバーは既存のものを利用） |
| 3 | 開発ツール | AI（Claude）をペアプログラミング的に活用 |

### 8.4 外部制約

| # | 制約 | 内容 |
|---|---|---|
| 1 | 駅データ | 外部APIサーバー (toyohide.work) から取得する |
| 2 | 都道府県ポリゴン | ローカルJSON (assets/json/japan_pref.json) から取得する |
| 3 | 地図タイル | OpenStreetMapのタイルサーバーから取得する（インターネット接続必要） |
| 4 | ネットワーク | 初回起動時の駅データ取得にはインターネット接続が必要 |
| 5 | 対応路線 | APIが提供する全国の路線・駅データに限定される |

## 9. リスクと対策

| リスクID | リスク | 影響度 | 発生確率 | 対策 |
|---|---|---|---|---|
| R-01 | ジオフェンスイベントがOSの省電力設定で遅延・無効化される | 高 | 中 | 利用者に省電力設定の解除を案内する。Android向けにloiteringDelayを設定する |
| R-02 | ユーザーが「常に許可」パーミッションを拒否する | 高 | 中 | パーミッション要求前に必要性を説明するUIを設ける |
| R-03 | 駅データAPIサーバーが停止する | 中 | 低 | エラーハンドリングを実装。アプリはクラッシュしない |
| R-04 | iOSとAndroidでジオフェンスの挙動が異なり品質にばらつきが出る | 中 | 高 | プラットフォーム別の設定値を調整する。実機テストを徹底する |
| R-05 | 全国の駅データが多量でAPIレスポンスが遅くなる | 中 | 中 | 都道府県単位でデータを取得する設計にして1リクエストの量を抑える |
| R-06 | APIの駅データに誤った順序・欠落・誤座標が含まれる | 中 | 高 | データ修正ロジック（DataRepair）で補正する |
| R-07 | 半年後にコードの意味を忘れる | 中 | 高 | 設計書を整備し、重要な実装意図をコメントに残す |

## 付録A: 用語集

| 用語 | 意味 |
|---|---|
| ジオフェンス | 地図上に仮想的な境界線（フェンス）を設定し、デバイスがその範囲に入った・出たときにイベントを発火する機能 |
| 乗り越し | 電車で目的の駅を通り過ぎてしまうこと |
| 都道府県ポリゴン | GeoJSON形式で定義された都道府県の境界座標の集合。地図上に形状として描画できる |
| 近傍駅 | 現在地から一定半径以内にある駅。Geolocatorで取得した現在地と各駅の座標距離で判定する |
| バックグラウンド動作 | アプリが画面に表示されていない状態（または終了状態）でも機能すること |
| DataRepair | APIの駅データの誤りを補正するロジック。駅順補正・路線番号マージ・手動パッチ適用の3段階がある |
| Riverpod | Flutter向けの状態管理ライブラリ |
| flutter_map | FlutterでOpenStreetMapを含む地図を表示するオープンソースライブラリ |
| Geolocator | FlutterでGPS位置情報を取得するパッケージ |
| パーミッション | アプリがOSの機能（位置情報・通知など）を利用するためのユーザー許可 |
